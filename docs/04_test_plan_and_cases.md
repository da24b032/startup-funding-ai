# 4. Test Plan, Test Cases and Test Report

## 1. Objectives and scope
Verify that the pipeline, API, UI and monitoring meet the acceptance criteria below. Tests are layered:

| Level | What | How |
|---|---|---|
| Unit | Schema validation, feature engineering, drift monitor, run log | `pytest` (no server) |
| API / integration | Every endpoint, validation and error paths, metrics exposure | `pytest` + FastAPI `TestClient` against the real trained model |
| Pipeline | Split correctness, artifact traceability, saved pipeline accepts raw rows | `pytest` (`test_data.py`, `test_training.py`) and `dvc repro` |
| UI | All four pages render, a form submission returns a result, backend-down message | Streamlit `AppTest` + manual checklist (§5) |
| System / ops | Docker Compose stack, Prometheus targets, Grafana dashboard | Manual checklist (§5) |

**Environment:** Python 3.11, dependencies from `requirements-dev.txt`, model produced by `dvc repro`. Run: `make test` (writes `reports/test_report.xml`). The same command is the DVC `test` stage, so the report is regenerated by the pipeline.

## 2. Acceptance criteria
| ID | Criterion | Evidence |
|---|---|---|
| AC-1 | Pipeline reproduces from raw data with one command and ends with all tests green | `dvc repro` → `prepare`, `train`, `test` stages succeed |
| AC-2 | Held-out test ROC-AUC ≥ 0.80 for the served model, chosen without using the test set | `reports/metrics.json` (0.8378), TC-T2 |
| AC-3 | Every invalid input is rejected with HTTP 422 and a request id; no input causes HTTP 500 | TC-A5…A9 |
| AC-4 | Every served model is traceable to commit hash, data hash and MLflow run id | TC-T1, TC-A10 |
| AC-5 | Prometheus metrics for requests, errors, predictions, drift and pipeline are exposed | TC-A11 |
| AC-6 | Frontend works through REST only and shows a friendly message when the backend is down | UI-1…UI-5 |
| AC-7 | Median single-row inference latency under 100 ms | `reports/metrics.json` (`latency_ms_single_row` ≈ 24 ms) |
